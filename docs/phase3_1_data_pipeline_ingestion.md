# Phase 3.1 — Data Pipeline & Ingestion Foundation
**Industrial Datalogger Analysis Application**
**Document Version:** 1.0.0
**Target Environment:** Linux / Windows / Edge Gateway / Raspberry Pi ARM64

## 1. Architecture Overview

Phase 3.1 establishes the foundational data ingestion pipeline for the Industrial Datalogger Analysis Application. It connects field telemetry generated by the Phase 2 communication engines (`PollingEngine`, Modbus RTU, Modbus TCP) to persistent MariaDB storage, instantaneous in-memory caching, real-time WebSocket distribution, and responsive web monitoring interfaces.

```
+-----------------------------------------------------------------------------------+
|                            FIELD HARDWARE / TRANSDUCERS                           |
|       (Solar Inverters, Flow Meters, RTUs, PLCs, Energy Meters, Sensors)          |
+-----------------------------------------------------------------------------------+
                                         │
                                         ▼ [RS485 RTU / Ethernet TCP]
+-----------------------------------------------------------------------------------+
|                        PHASE 2 COMMUNICATION ENGINE                               |
|   ConnectionManager ──► Modbus RTU / TCP Adapters ──► PollingEngine Worker Loops   |
+-----------------------------------------------------------------------------------+
                                         │
                                         ▼ Telemetry Ingest Payload (Non-Blocking)
+-----------------------------------------------------------------------------------+
|                       DATA PIPELINE INGESTION SERVICE                             |
|                                                                                   |

|  2. Normalization (Numeric double, Formatted Text, Boolean ON/OFF, Raw Hex/Wire)  |
|  3. Instantaneous In-Memory Cache (O(1) Map for Dashboard Reads)                 |

+-----------------------------------------------------------------------------------+
               │                                                    │
```

## 2. Telemetry Ingestion Flow

1. **Acquisition:** The isolated `PollingEngine` device worker executes Modbus read requests (`ReadHoldingRegisters` / `ReadInputRegisters` / `ReadCoils`).
2. **Decoding & Scaling:** Raw bytes are decoded per register layout (`FLOAT32`, `INT16`, `UINT32`, `BOOLEAN`) and byte order (`ABCD`, `CDAB`, `BADC`, `DCBA`). Engineering scaling formula $V = (R \times \text{Scale}) + \text{Offset}$ is applied.
3. **Dispatch:** `PollingEngine.ReadParameter` calls `TelemetryService.Ingest(&TelemetryIngestPayload{...})`.
4. **Validation & Normalization:** Ingestion validates device and parameter IDs, sanitizes `NaN`/`Inf` inputs, assigns quality codes (`GOOD`, `BAD`, `UNCERTAIN`, `UNKNOWN`), and generates normalized representations (`ValueNumeric`, `ValueText`, `ValueBool`, `RawHex`).
5. **Instantaneous In-Memory Cache:** The latest value is immediately updated in an in-memory `sync.RWMutex`-protected map.
6. **Realtime Broadcast:** The normalized telemetry item is broadcast to all active browser sessions via WebSocket (`device.telemetry.received`).
7. **Buffered Persistence:** The item is enqueued into a bounded channel. If the queue is saturated, the event is dropped with a logged warning and metric increment, guaranteeing communication workers are never blocked by database I/O latency.
8. **Batch Flush:** Background persistence worker flushes batches (up to 50 items or 250ms interval) into MariaDB within an atomic transaction.

## 3. Telemetry Data Model

### MariaDB `raw_data` Schema

| Column | Type | Nullable | Description |
|---|---|---|---|
| `id` | BIGINT UNSIGNED AUTO_INCREMENT | NO | Unique sequence primary key |
| `device_id` | INT UNSIGNED | NO | Owning device foreign key |
| `parameter_id` | INT UNSIGNED | NO | Parameter definition foreign key |
| `value` | DOUBLE | NO | Scaled engineering value |

| `value_text` | VARCHAR(255) | YES | Formatted string / status ("ON", "OFF", "28.46") |
| `value_bool` | TINYINT(1) | YES | Boolean state (1 = true, 0 = false) |

| `stored_at` | DATETIME(3) | NO | UTC MariaDB commit timestamp |
| `timestamp` | DATETIME(3) | NO | Backward compatibility alias |
| `created_at` | DATETIME(3) | NO | Record creation timestamp |

## 4. Timestamp Strategy

Industrial sensors may lack internal real-time clocks (RTC) or provide asynchronous timestamps:
- `device_timestamp`: Set only if the field device or protocol supplies an explicit timestamp. Otherwise `NULL`.
- `received_at`: Exact timestamp (UTC) when the datalogger edge gateway received and decoded the telemetry frame. **Always mandatory.**
- `stored_at`: Exact timestamp (UTC) when the batch persistence worker committed the record into MariaDB.
- `timestamp`: Synced to `received_at` for Phase 1 backward compatibility.

All timestamps are stored internally in UTC (`time.Now().UTC()`). The web frontend renders timestamps in the operator's local browser timezone with seconds resolution.

## 5. Quality Model

Data quality follows industrial telemetry conventions (OPC-UA / IEC 60870):

| Quality | Code | Description |
|---|---|---|
| `GOOD` | 192 | Verified readout within valid limits, normal communication |
| `BAD` | 0 | Communication failure, parity/CRC error, NaN/Inf value, timeout |
| `UNCERTAIN` | 64 | Value suspect, out of expected warning range, or connection degraded |
| `UNKNOWN` | 32 | Unitialized parameter, standing by for first field acquisition |

## 6. Raw Data vs. Latest Value Separation

To prevent expensive full-table scans on `raw_data` when dashboards and monitoring panels query current states:
1. **Instantaneous In-Memory Cache:** `TelemetryService.latestCache` provides $O(1)$ memory lookups in microseconds.
2. **Persisted Latest Values:** The `parameters` table stores `current_value`, `current_value_numeric`, `current_value_text`, `current_value_bool`, `current_quality`, `current_raw_hex`, and `current_received_at`.
3. **Audit & History:** The `raw_data` table stores every persistent telemetry point for audits, trends, exports, and analytics.

---

## 7. Buffered Persistence & Backpressure

To support resource-constrained hardware (Raspberry Pi, industrial ARM gateways):
- **Bounded Buffer:** Fixed Go channel capacity (default 5,000 items).
- **Non-Blocking Ingestion:** Pushes to the buffer use non-blocking `select`. If the buffer fills due to database lockups, incoming telemetry is dropped with a metric increment rather than stalling communication loops.
- **Batching:** Flushed every 50 records or 250 milliseconds.
- **Transient Failure Retry:** Up to 3 attempts with exponential backoff (100ms, 200ms, 400ms).

---

## 8. Graceful Shutdown & Flush

On `SIGINT` or `SIGTERM`:
1. Polling engine workers stop acquiring new telemetry.
2. `TelemetryService.Stop()` is invoked:
   - Sets stopped flag to reject new incoming calls.
   - Context cancelled to signal persistence worker.
   - Buffer is drained and all remaining in-flight records are committed to MariaDB.
   - Waits for worker completion with `sync.WaitGroup`.
3. HTTP server shuts down with 5s timeout.
4. Database connections cleanly closed.

## 10. Telemetry REST API

All endpoints require JWT Authentication and RBAC permission `device.view`:

- `GET /api/devices/:id/telemetry/latest`: All latest parameter values for device `:id`.
- `GET /api/devices/:id/parameters/:paramId/telemetry/latest`: Latest value for a single parameter.
- `GET /api/devices/:id/telemetry/history`: Paginated historical records.
  - Query parameters: `parameter_id`, `start_time`, `end_time`, `quality`, `page`, `page_size`.
- `GET /api/devices/:id/telemetry/raw`: Raw packet frames and hex data for troubleshooting.
- `GET /api/telemetry/metrics`: Ingestion throughput, buffer length, dropped count, and flush timings.

---

## 11. Database Indexing Strategy

Composite and targeted indexes on `raw_data`:
- `idx_raw_dev_param_rec (device_id, parameter_id, received_at)`: Primary composite index for parameter historical queries.
- `idx_raw_dev_rec (device_id, received_at)`: Device-level time-series queries.
- `idx_raw_rec (received_at)`: Retention pruning and global range queries.
- `idx_raw_param (parameter_id)`: Quick parameter lookups.
